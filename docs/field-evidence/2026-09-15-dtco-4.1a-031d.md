## Change under test

Earlier field runs showed a repeatable pattern: the first RDBI request sent immediately after a positive TesterPresent response could time out, while subsequent DID reads succeeded.

0.31d keeps the same one-pass read-only sequence but inserts a 1-second transport-settling delay after positive TesterPresent and before the first RDBI request:

`TesterPresent -> 1 s -> F923 -> F925 -> F903 -> F99A -> F99B`

No Remote HMI/F211 session and no `10 7E` session switch are used by this candidate.

## Conclusion

For this DTCO 4.1a / Android Chrome / Diagnostics BLE path, the 1-second settling delay removed the previously observed first-RDBI timeout pattern across four consecutive complete runs. The evidence supports keeping the 0.31d request order and timing unchanged unless a new reproducible failure is observed.

Do not generalize this result to untested tachograph models, firmware versions, browsers, or BLE implementations without separate field validation.
